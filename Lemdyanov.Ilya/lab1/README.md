# Вариант 20 Disk Monitor 

Демон на C++17 для Linux, который отслеживает файловые события в заданных каталогах с помощью `inotify` и записывает их в отдельный журнал. Служебные сообщения — запуск, ошибки, перезагрузка конфигурации и завершение — отправляются в syslog с facility `LOG_LOCAL0` через `openlog()`, `syslog()` и `closelog()`.

## Сборка

Из корня проекта выполните:

```bash
./build.sh
```

Скрипт собирает исполняемый файл `disk-monitor`, используя CMake и компилятор C++, с флагами `-Wall -Wextra -Wpedantic -Werror`. Временные файлы сборки удаляются автоматически.

Альтернативный способ — собрать проект напрямую через CMake:

```bash
cmake -S . -B cmake-build-debug
cmake --build cmake-build-debug
```

## Запуск и управление

Для конфигурации из примера (ниже) создайте рабочие каталоги и соберите программу:

```bash
mkdir -p watch logs run
./build.sh
./disk-monitor ./daemon.conf
```

`watch/` — каталог для наблюдения, `logs/` — место для `events.log`, `run/` — место для PID-файла. Команда `mkdir -p` создаёт отсутствующие каталоги и не сообщает об ошибке, если они уже существуют. Каталоги, указанные в `directories`, должны существовать до запуска.

После успешной демонизации процесс запуска завершается, а демон продолжает работать в фоне. Команды ниже предполагают, что в конфигурации указан `pid_file=./run/disk-monitor.pid`:

```bash
# Перечитать конфигурацию
kill -HUP "$(cat run/disk-monitor.pid)"

# Остановить демон
kill -TERM "$(cat run/disk-monitor.pid)"
```

PID-файл удаляется при штатном завершении. Файл `disk-monitor.pid.lock` может остаться: это отдельный файл блокировки, обеспечивающий стабильный inode для `flock()` при повторных запусках. Если блокировка уже занята, новый экземпляр завершает запуск с ошибкой.

## Конфигурация

По умолчанию программа читает `daemon.conf` из текущего рабочего каталога. Можно передать путь к другому файлу аргументом командной строки. При запуске абсолютный путь к конфигурации сохраняется для последующего перечитывания по `SIGHUP`.

Пример `daemon.conf`:

```ini
interval_seconds=5
directories=./watch
event_log=./logs/events.log
pid_file=./run/disk-monitor.pid
```

Параметры:

- `directories` — обязательный список существующих каталогов, разделённых `;`.
- `event_log` — файл журнала файловых событий; по умолчанию `disk-monitor.log`.
- `pid_file` — путь к PID-файлу; по умолчанию `disk-monitor.pid`.
- `interval_seconds` — целое число от `1` до `86400` (по умолчанию `5`). Параметр проверяется при чтении конфигурации, но частота обнаружения событий определяется `inotify`, а не этим интервалом.

Относительные пути отсчитываются от каталога, в котором находится конфигурационный файл. Абсолютные пути используются без изменения, кроме нормализации. Пустые строки и строки, начинающиеся с `#`, игнорируются; неизвестные параметры и некорректные значения считаются ошибкой.


## Журналы

- **Журнал файловых событий** — путь задаётся параметром `event_log`; каждая запись содержит время, тип события и путь к файлу или каталогу.
- **Системный журнал** — содержит сообщения о запуске, остановке, сигналах, ошибках и перечитывании конфигурации. Используется facility `LOG_LOCAL0`; способ просмотра зависит от конфигурации системы. Например, можно попробовать `journalctl -t disk-monitor`.

## Тестирование

Проект содержит C++ unit-тесты для `Config`, `DirectoryMonitor` и `Daemon`, а также интеграционный тест `tests/smoke_test.sh`, который запускает реальный демон во временном каталоге и проверяет демонизацию, PID-файл, блокировку второго экземпляра, файловые события, сигналы и перезапуск. Внешний C++-фреймворк для тестирования не требуется.

Собрать приложение и тесты и запустить все зарегистрированные проверки:

```bash
cmake -S . -B cmake-build-debug
cmake --build cmake-build-debug
ctest --test-dir cmake-build-debug --output-on-failure
```

Запустить только unit-тесты или только интеграционный тест:

```bash
ctest --test-dir cmake-build-debug --output-on-failure -L unit
ctest --test-dir cmake-build-debug --output-on-failure -L integration
```

Интеграционный тест использует временные файлы и каталоги и удаляет их после завершения. Проверка видимости системных сообщений может быть пропущена, если у текущего пользователя нет доступа к системному журналу.
